Prompt engineering

How we make the guidance work for the creator's assistant: skills, plan templates, AGENTS.md, llms.txt and the messages of the tooling. We judge it by one thing: does the assistant follow the process? An app built by the process is good when its creator knows the subject, so content quality is not scored.

How we work

  1. Interactive test. One real creator session with a person as the creator, on a small app. We read the transcript: which instructions were followed, which ignored, which links never opened, where GitHub got in the way.
  2. Evals. The same scenarios across assistant configurations, several runs each, with a simulated creator; scored per expectation from the app folder and the transcript. Results below.
  3. Changes. Each finding becomes a change to the guidance or the tooling, as short, hard rules where the step happens, or as a check when a rule keeps being skipped.
  4. Interactive test of the new guidance. Before a change is published, a person builds one small app with it. The assistant runs in a separate Claude Code session on the web and gets the unpublished guidance from the orchestrating session: instead of opening a URL on lernapps.net or GitHub, it sends GET <url> to that session and waits for the content. The orchestrator answers from the working copy, can change a file between two requests without publishing, and logs every request. The CLI still comes from npm, so the assistant treats the guidance copied into the app as outdated and asks for it too. Then the evals again, comparing the new guidance with the old in the same configurations.

The assistant knows it is in a test, and each request costs a turn: good enough to iterate fast, not a measurement. Measurements come from the evals.

How an eval works

The whole method, with a diagram of a trial and the reasons behind it: How we evaluate the guidance.

An eval tests an assistant configuration (harness, its version, model) on our guidance: does the creator's assistant follow it from the creator's first prompt to the publish checkpoint? We judge the process, not the content.

  • Scenarios: each starts from an empty folder with the build prompt of lernapps.net/apps/build: a quiz, an explainer and an interactive app (a typing trainer). A simulated creator answers from a persona and ends before anything is pushed: a question about GitHub gets “no repo, work locally”, the question to publish gets “stop”, an agent that says it is done gets “thanks”. It marks its last message with the end ([Ende: veröffentlichen], fertig, festgefahren). The row “Code done” counts a green check and a regular end after the plan.
  • Scores: a verifier scores the app folder at the end (plan, app, git); a second script scores the transcript (what the agent read, asked and ran, and which skills it loaded in which phase). Each row measures one or more expectations (A1–A34 in the plan of the evals).
  • A run is a matrix of scenarios and models at one commit of the guidance, three times each where the subscription allows. Configurations are never mixed: a re-run at a newer guidance is its own column.
  • Cleaned: a trial that hit the subscription's usage limit (HTTP 429) or broke off before its agent started is no result and is left out; a job the orchestrator ruled out (a harness fault) too. A trial whose verifier crashed stays in without the verifier's numbers. Each such case is listed with its reason under the run.
  • Conclusions: the numbers come from the runs alone; what we concluded from them, and what we did about it, is written and reviewed separately. Every finding links the cells it rests on.

Findings

What the numbers show. Each finding links the cells it rests on.

  1. Haiku 5.5 keeps to the process on the interactive app

    All three runs pass the check, tick 94–100 % of the plan's boxes, fill the content guide, create the app only after the plan's yes and need one to three creator turns after it. Two set phase: commit and then asked for the repo in a reply that began "**Commit · Checkpoint**"; the third asked for the publish yes while still in Code. On 2026-10-21 (guidance b20b514) the same cell passed the check in 1 of 3 runs and set phase: commit in none. With n = 3 this is a sign, not a proof.

    Evidence: Interactive · Haiku 5.5 · lernapps check passes 100 % · Interactive · Haiku 5.5 · Phase in the plan at the end (commit = 100 %) 89 % · Interactive · Haiku 5.5 · No app created before the plan was confirmed 100 % · Interactive · Haiku 5.5 · At most 3 creator turns after the plan 100 %

  2. Most replies begin with the phase, and it is the plan's

    Two runs began every reply the creator read with the phase ("**Explore · Checkpoint**", "**Plan · Checkpoint**", "**Code**"); the third began only 2 of 8, narrating first ("Die Antworten sind klar…"). No reply named a phase the plan did not hold. Code was announced in one run only: in the other two the whole Code phase ran inside one turn, whose reply already began with Commit.

    Evidence: Interactive · Haiku 5.5 · Replies that begin with the phase 75 % · Interactive · Haiku 5.5 · Announced phase is the plan's 100 %

  3. The browser tests could not press ä, ö, ü or ß

    The interactive template's end-to-end test pressed each key of a playthrough with Playwright's keyboard.press, which knows only the keys of a US keyboard: "Unknown key: ö" (and Ä, ä, ß). The check called it a template bug, and every run got around it by rewriting its playthroughs so that they never press those keys. That is also why the check failed in 2 of 3 runs on 2026-10-21, where the tests stayed red.

    Evidence: Interactive · Haiku 5.5 · lernapps check passes 100 %

  4. The creator did not send its end marker

    The simulated creator wrote the marker [Ende: …] only into its own summary, never into a message to the agent; the score fell back to the creator's sentences. In one run it ended without sending its last message at all, so the scenario's end and "Code done" read 0 there, which is the creator's mistake, not the agent's.

    Evidence: Interactive · Haiku 5.5 · Code done: check green and the scenario ended after the plan 67 %

  5. Skills in their phase and the questions per turn stay as they were

    Haiku loads 14–57 % of the skills a phase names by its end (38 % on 2026-10-21), and every run loads one before its phase. Every run asks more than two questions in a turn (at most 4–5).

    Evidence: Interactive · Haiku 5.5 · Skills loaded in their phase 33 % · Interactive · Haiku 5.5 · At most 2 questions in every turn 0 %

Findings

What the numbers show. Each finding links the cells it rests on.

  1. Sonnet 5.5 and Opus 5.5 follow the process

    They wrote the competencies, filled the content guide, chose the right archetype, passed the check, reached the commit phase and committed clean in every run, with one exception: Opus 5.5 left the content guide empty in 1 of 2 interactive runs. They ticked 93–100 % of the plan's boxes on average.

    Evidence: Interactive · Opus 5.5 · Content guide filled (app-content) 50 % · Explainer · Sonnet 5.5 · Plan boxes ticked 100 %

  2. Haiku 5.5 passes the check but skips process steps

    Haiku 5.5 passed the check in 14 of 14 runs, but filled the content guide in only 2, ticked between 0 and 100 % of the plan's boxes per run (mean 70 % quiz, 46 % explainer, 7 % interactive), wrote no competencies in any interactive run, chose the wrong archetype once (an explainer for the typing trainer) and created the app before the creator confirmed the plan in 4 runs (2 of 3 interactive, 1 of 5 explainer, 1 of 6 quiz). Every run reached the scenario's end with a green check ("Code done"); in 2 of 5 explainer runs it did so without setting phase: commit.

    Evidence: Quiz · Haiku 5.5 · Content guide filled (app-content) 17 % · Interactive · Haiku 5.5 · Plan boxes ticked 7 % · Interactive · Haiku 5.5 · Archetype chosen right 67 % · Explainer · Haiku 5.5 · Phase in the plan at the end (commit = 100 %) 87 % · Explainer · Haiku 5.5 · Code done: check green and the scenario ended after the plan 100 % · Interactive · Haiku 5.5 · No app created before the plan was confirmed 33 %

  3. No model keeps to one or two questions per turn

    32 of 33 runs asked more than two questions in one turn: Haiku 5.5 at most 2–7, Sonnet 5.5 4–8, Opus 5.5 4–12. The score counts sentences that end in "?" in the agent's text, so questions inside a plan draft count too.

    Evidence: Quiz · Sonnet 5.5 · At most 2 questions in every turn 0 % · Explainer · Opus 5.5 · At most 2 questions in every turn 0 %

  4. Opus 5.5 is slower, not better

    Opus 5.5 took 60 minutes on the explainer against 24 for Sonnet 5.5 (2.5 times), 41 against 21 on the interactive app and 24 against 20 on the quiz, and read 3.5 times as many cached tokens on the explainer.

    Evidence: Explainer · Opus 5.5 · agent minutes 59.9 · Explainer · Sonnet 5.5 · agent minutes 23.8

  5. Every run read guidance through a summarising fetch

    Every run fetched guidance through a summarising fetch tool at least once; 32 of 33 also downloaded the plan template and read it word for word.

    Evidence: Quiz · Haiku 5.5 · Plan template read word for word 100 %

Limits

  • Small n: 2 to 6 runs per cell. One creator model (Haiku 5.5).
  • The creator decides each message in a fixed format since 22 October, so its own mistakes count apart from the agent's. Runs before that read its end from its free text, and before 21 October from its sentences.
  • Fresh scenarios only: no increment, no prepared start states yet.
  • GitHub only as a local remote in the container; the GitHub cases on github.com are not run yet.
  • Claude Code so far; OpenCode is prepared (HARNESS=opencode), Codex and Gemini CLI are not run yet.
  • Harbor's own token and cost numbers are wrong for the agent behind the ACP bridge; the tokens here come from the agent's ACP session, or, where it reports none there, from Claude Code's own log.

How to run it, in detail

What it needs

  • A machine with Docker (the daemon is started by setup.sh if none runs), uv and Node 22. In a Claude Code cloud container this is all there.
  • A credential in EVALS_ANTHROPIC_API_KEY: an API key, or a subscription token from claude setup-token. In a cloud environment, store it as an environment variable under that name; names starting with ANTHROPIC_ are filtered out by the platform.
  • About 2 GB of disk for the task image and up to 1.5 GB per running trial.

Steps

  1. evals/harbor/setup.sh installs Harbor 0.24.0 into ~/.lernapps-evals, applies the patches in evals/harbor/ (the subscription token for the ACP bridge, the acpx config outside the app folder) and writes the generated files into each task.
  2. evals/harbor/run.sh <task> <model> [trials] [concurrency] runs one Harbor job. The tasks are quiz-fresh, explainer-fresh and interactive-fresh; the model is a Harbor name such as anthropic/claude-sonnet-5-5; HARNESS names the assistant (claude-code by default, or opencode with EVALS_OPENCODE_API_KEY); USER_MODEL sets the simulated creator (default: the same model for Claude Code, Haiku 5.5 otherwise). Harbor runs through evals/harbor/harbor.sh, which clears the environment, so no other credential reaches the containers. The job lands in ~/.lernapps-evals/jobs with its configuration.json and the transcript score.
  3. For a matrix, start one run.sh per model in parallel; two or three at a time fit a machine with 4 CPUs and 16 GB. Watch the rate_limit_event lines in <trial>/user-agent/claude-code.txt and stop at a limit.
  4. node evals/summary.ts ~/.lernapps-evals/jobs prints mean, min and max per dimension for each task and configuration while a run goes on; configurations are never mixed.
  5. node evals/results.ts <run> ~/.lernapps-evals/jobs writes the run's evals/runs/<run>/results.json: the numbers, cleaned as above. A job with an excluded.txt (its reason inside) is left out.
  6. Write evals/runs/<run>/conclusions.yaml beside it: the question, the bottom line, the findings with the cells they rest on, and what we did about them. The site's build renders this page from both and fails when a finding names a cell or row the run does not have.
