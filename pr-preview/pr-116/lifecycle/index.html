lernapps.net tooling

From a person's goal to a published app

A creator knows what learners should be able to do afterwards. An AI assistant can build the app. The platform keeps the two aligned and asks the person only for what is theirs to decide: what the app is for, what it teaches and whether it goes out. The technical decisions are taken once, by the platform.

The app is deterministic: it does the same every time. The assistant that builds it is not. So deterministic checks surround a probabilistic builder, and we measure where the person was still needed.

What runs through every phase comes first, then the four phases. Each box is a part of the tooling and links to its place in the architecture. Hover over a box, or move to it with the keyboard, to read what it does for whom. A dashed box is planned and not built yet.

  • Person decides or is asked
  • AI agent works from it

Across all phasesWhat runs through every phase?

  • Process guidance

    Person Reads the compact write-up of the plan and confirms it at the checkpoints.

    AI agent Keeps the process, works the plan step by step, takes notes and stops for the person at each checkpoint.

  • Process support

    AI agent Asks the right questions for the phase it is in, and knows the rules every app follows and how to get past a GitHub step.

101

Plan and scopeWhat is the app for, and for whom?

The person decides

What the app is for, who the learners are and what they should be able to do. The creator confirms the plan.

  • Exploration

    Person Brings the domain knowledge: the subject, the grade and their own material.

    AI agent Proposes options, researches the curriculum and the sources, and applies pedagogical guidance.

202

BuildHow do the goals stay consistent while the assistant builds?

  • Generator

    AI agent Installs the chosen archetype: writes the app from its template once the plan is confirmed and pins the tooling and runtime it came from. The app passes every check from the first commit.

  • Archetypes

    AI agent Is the kind of app: a working template, the runtime that runs it and a preset of toolchain and git hooks that the app imports and never edits. The agent writes only the content, or the code where the kind leaves it free.

  • Lint rules

    AI agent Marks a problem in the code while it writes, such as a request to another host. Each message says what to fix.

  • Conventions in build

    AI agent Knows how the chosen kind of app works, what to write in it and what the build checks, and grows the app one competency at a time.

303

Test and roll outDoes the app hold, and does it go out?

The person decides

Whether the app goes online. Neither a check nor the review decides whether the content teaches correctly.

Decided by a program

Same result in the hooks, in CI and at the listing.

  • Check CLIrule id

    AI agent Runs every check of the app, reads each message and fixes what it says.

  • Git hooksrule id

    AI agent Run the fast part of the check before a commit and the heavy part before a push, whichever assistant commits.

  • App check actionrule id

    AI agent Runs in CI what the hooks ran, and keeps the report and the checked bundle.

Released at the person's yes

The app that goes online is the one that was checked. It lives at its developer's own address.

  • App preview

    Person Looks at the increment in the real app before saying yes.

    AI agent Puts the checked bundle of a pull request online as a temporary preview and says where it is.

  • App publish

    Person Looks at the preview of the app and says yes before it goes online, and makes the one click only an admin can make.

    AI agent Publishes the checked bundle, names the address and says what to change if a setting is missing.

Listed in the app overviewOptional

Tells adults the app exists and puts the platform's name on it. Judged by an agent first, then decided by the owner.

  • Listing validationrule id

    Person The creator sees the listing pull request and its result and gives their word before anything in it changes. The owner decides on the listing.

    AI agent The assistant opens the listing pull request, which is the review, and sees it through to "bestanden". The validation runs the checks against the deployed app and comments the report.

  • Review procedurerubric item id

    Person The owner starts the review, reads the verdict and decides on the listing.

    AI agent A fresh agent judges what no check can decide against the rubric. Every finding names a rule id.

A judgment may vary. The goal it judges does not.

404

MonitorWhere were the goals not held?

The person decides

Which guesses and problems become rules. The owner decides.

  • Process guidance

    Person The owner reads the retrospective when an app asks to be listed: how far the plan got, how often the person was needed after it, and where the agent had to guess.

    AI agent Writes the retrospective at the end of the plan, and the hooks count the failed checks and pushes in its front matter.

  • Evals

    AI agent Runs sample prompts of a simulated creator against the guidance with several assistants, and scores the result by the check, the review and the plan's counters.

  • Review procedure

    Person The owner reads the proposed rules and decides which are taken.

    AI agent Turns a guess in the retrospective, or a problem no rule covers, into a proposed rule and says where it would act.

  • Evaluating agent sessionsPlanned, not builtStarting with the owner's own sessions.

    Person Would let the owner read the sessions they own, and later exports that contributors send in.

    AI agent Would evaluate a session for where the assistant guessed, stalled or needed the person.

Every check answers to a goal with an id

A program decides what a program can decide: one check, the same wherever it runs, whose rules each have an id in the rule catalog. What no program can decide is judged by a review agent in a fresh context against the items of a published rubric, each with an id as well. A judgment may vary from one run to the next. The goal it judges does not.

Neither judges whether the content teaches correctly. That stays with the person.

How we know

The platform collects nothing from apps in use, so what it measures is the process that makes them. The baseline is the eval run of 18 October 2026: 33 runs with a simulated creator, on three archetypes and three assistant models.

  • 33 of 33runs where lernapps check passed at the end
  • 25 of 33runs where the simulated creator was needed at most 3 times after the plan, which is the target
  • 0git hooks bypassed, and no failed pre-push run

The weakest of the three models needed more turns. The retrospective that records guesses is not available for 23 of the 33 runs, because they stop before the listing. The numbers say how well the guidance holds for an assistant, not how real creators fare. The runs, their table and what we changed because of them are on Prompt engineering.

What is not covered yet

  • Monitor is the weakest phase, by designThe platform collects nothing from apps in use. It has no runtime telemetry, no scheduled run that shows drift when a model changes, and it does not measure the cost of a session.
  • Reading the sessions of the assistant is plannedFirst the owner's own sessions, later session exports that contributors send in. Not built.
  • Reports do not become feedback by themselvesTurning the retrospectives into issues automatically is an idea. It would need the creator's consent, because nothing leaves unasked.
  • The goals of an app are textThe competencies are written in the plan and are not machine-readable yet.
  • Nothing asks whether an app is needed at allPlan and scope surfaces the goals; it does not weigh them against existing apps.
  • Listed apps are not checked again over timeNot by this tooling.
