lernapps.net tooling

From a person's goal to a published app

A creator knows what learners should be able to do afterwards. An AI assistant can build the app. The platform keeps the two aligned and asks the person only for what is theirs to decide: what the app is for, what it teaches and whether it goes out. The technical decisions are taken once, by the platform.

The app is deterministic: it does the same every time. The assistant that builds it is not. So deterministic checks surround a probabilistic builder, and we measure where the person was still needed.

What runs through every phase comes first, then the four phases. Each box is a part of the tooling and links to its place in the architecture. Hover over a box, or move to it with the keyboard, to read what it does for whom. A dashed box is planned and not built yet.

Every check answers to a goal with an id

A program decides what a program can decide: one check, the same wherever it runs, whose rules each have an id in the rule catalog. What no program can decide is judged by a review agent in a fresh context against the items of a published rubric, each with an id as well. A judgment may vary from one run to the next. The goal it judges does not.

Neither judges whether the content teaches correctly. That stays with the person.

How we know

The platform collects nothing from apps in use, so what it measures is the process that makes them. The baseline is the eval run of 18 October 2026: 33 runs with a simulated creator, on three archetypes and three assistant models.

  • 33 of 33runs where lernapps check passed at the end
  • 25 of 33runs where the simulated creator was needed at most 3 times after the plan, which is the target
  • 0git hooks bypassed, and no failed pre-push run

The weakest of the three models needed more turns. The retrospective that records guesses is not available for 23 of the 33 runs, because they stop before the listing. The numbers say how well the guidance holds for an assistant, not how real creators fare. The runs, their table and what we changed because of them are on Prompt engineering.

What is not covered yet

  • Monitor is the weakest phase, by designThe platform collects nothing from apps in use. It has no runtime telemetry, no scheduled run that shows drift when a model changes, and it does not measure the cost of a session.
  • Reading the sessions of the assistant is plannedFirst the owner's own sessions, later session exports that contributors send in. Not built.
  • Reports do not become feedback by themselvesTurning the retrospectives into issues automatically is an idea. It would need the creator's consent, because nothing leaves unasked.
  • The goals of an app are textThe competencies are written in the plan and are not machine-readable yet.
  • Nothing asks whether an app is needed at allPlan and scope surfaces the goals; it does not weigh them against existing apps.
  • Listed apps are not checked again over timeNot by this tooling.
